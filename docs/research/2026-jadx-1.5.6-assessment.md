# jadx 1.5.6: what it changes, and what we should build on it

> Follow-up to [`2026-jadx-capabilities.md`](2026-jadx-capabilities.md), which
> flagged 1.5.6 as worth adopting from its release notes. This is the version
> checked against the jars and both real APKs.
>
> **Status: adopted.** `pom.xml` is on 1.5.6. `jadx-analysis` was added alongside
> it for feature C and has since been removed again — see [§C](#c-replace-generatecallgraphformethod-with-jadx-analysis).
> Section 2 was re-measured on the large APK before the upgrade landed and turned
> out to understate the change — see [§2a](#2a-what-the-large-apk-actually-showed).
> **Feature A (`get_callees`) shipped**; its measured cost corrects the "~0 ms"
> estimate below, see [§A](#a-get_calleesclassname-methodname--highest-value-smallest-change).
> Section 3 then turned out to be reading a graph that decompilation edits
> underneath it, so `get_callees` was moved onto the dex instructions — and then
> so were all three `get_xrefs_to_*` tools and the sink sweep's in-APK half. See
> [§3a](#3a-getused-is-not-safe-to-read-from-a-shared-daemon) and
> [§3b](#3b-the-reverse-direction-closed).
> **Feature B (`find_sink_call_sites`) shipped**; §4's sweep held up, but the
> exact-name matching it was measured with turned out to miss real call sites —
> see [§B](#b-find_sink_call_sitessinks--the-most-interesting).
> **Feature C resolved by deletion, not by rebuild** — the regex call graph is
> gone and nothing replaced it; the reasoning and the measurements that decided
> it are in [§C](#c-replace-generatecallgraphformethod-with-jadx-analysis).

**Method.** API surface diffed with `javap` between `jadx-core-1.5.5.jar` and
`jadx-core-1.5.6.jar`; behaviour measured with throwaway probes against
`misc/DivaApplication.apk` (1,791 classes) and the a large production APK `app.apk`
(141,461 classes / 872,119 methods). Probe sources are reproduced at the end so
none of this has to be re-derived.

---

## 1. The upgrade is a drop-in

The public API of every jadx type this server calls — `JadxDecompiler`,
`JadxArgs`, `JavaClass`, `JavaMethod`, `JavaField`, `RootNode`, `ClassNode`,
`MethodNode`, `FieldNode`, `ClassInfo`, `MethodInfo`, `AType`,
`MethodOverrideAttr`, `ArgType`, `ClspGraph`, `ResContainer`, `ResourceFile`,
`ICodeInfo` — was diffed method by method.

**The diff is purely additive.** No removals, no signature changes, nothing
deprecated out from under us. Additions only:

| Type | Added in 1.5.6 |
|---|---|
| `JavaMethod` | `getUsed()`, `getUnresolvedUsed()`, `callsSelf()` |
| `MethodNode` | `getUsed()`, `getUnresolvedUsed()`, `callsSelf()`, `addUsed()`, setters |
| `JavaClass` | `loadingWouldRequireDecompilation()` |
| `ClassNode` | `getInnerClassesRecursive(Set)` |
| `AType` | `EXC_SPLIT_CROSS` |

Verified by building: `<jadx.version>1.5.6</jadx.version>`, no source changes,
**`mvn test` 60/60 green**. Adding the new `jadx-analysis` module alongside it —
also 60/60. Re-confirmed at adoption time: 60/60 Java and 30/30 Python, no source
change of any kind, only `pom.xml`.

## 2. Decompiled output changes, and improves

This is the one thing an upgrade could break, because every worker prompt in
`the analysis client` is written against `get_class_source` text.

Decompiled the same 60 DIVA classes under both versions and diffed:
**7 of 60 classes differ, 67 changed lines**, total output 1,086 chars shorter.
Every difference is loop restructuring getting better:

```diff
-        int i = 0;
-        while (true) {
-            if (i >= z) {
-                break;
-            }
+        for (int i = 0; i < z; i++) {
```

and a matching inversion that removes a level of nesting:

```diff
-            if ((flags & 2) == 0) {
-                i++;
-            } else {
+            if ((flags & 2) != 0) {
```

This is a readability win for the agents, not a risk — a `for` loop with its
bound in the header is far easier to reason about than `while (true)` plus a
break. It is still a behavioural change to output, which is why the upgrade
belongs in its own commit rather than riding along with a feature.

## 2a. What the large APK actually showed

Section 2 measured DIVA, where the classes are small and 1.5.5 already
decompiles all of them. Repeating it on a large production APK — 650 sampled classes: every
WebView/router/deeplink-named class, 150 `*Activity` classes, and a 250-class
even stride across all 72,345 top-level classes — found a **bigger and different**
change. Loop restructuring is real but it is not the headline.

| | |
|---|---|
| Classes byte-identical | 510 / 650 |
| Differ, decompilation coverage changed | 23 |
| Differ, rendering only | 117 |
| Methods 1.5.5 gave up on that **1.5.6 decompiles** | **28** |
| Methods 1.5.6 gives up on that 1.5.5 decompiled | 2 |
| Net output size | +275,734 chars (+4.8 %) |

`Method not decompiled` markers across the sample fall **33 → 7**, and
`Method dump skipped` **19 → 2**. The output grows because methods that used to
render as raw smali now render as Java. The most on-point example is
`com.example.app.SchemeDispatcher.m5984v(android.net.Uri)` — a deeplink
dispatcher, smali under 1.5.5, and under 1.5.6:

```java
String host = uri.getHost();
if (!TextUtil.isEmpty(host)) {
    int iHashCode = host.hashCode();
    ...
    if ("new".equals(uri.getQueryParameter("ddl"))) {
```

That is a route-enumeration worker's entire job, previously unreadable.

**The two regressions**, both isolated single methods:

- `com.example.addressnew…confirmnew.ConfirmFragmentEx.g0(...)` — `JADX ERROR: Types
  fix failed` (an NPE inside `TypeUpdate`). The same class gains `onPageEnter()`.
- `com.megvii.lv5.C28800e.mo63687g()` — no longer decompiled.

Neither is a WebView, router or deeplink surface. Where a method fails, 1.5.6
prints an explicit `JADX ERROR` with the exception, which is why the raw
`JADX ERROR` count rises 1 → 5 even though failures fall: three of those five sit
on methods that *already* failed silently under 1.5.5.

**Nothing was found that a worker prompt could misread.** The two things the
research was told to watch:

- *String literals.* Of 650 classes, 3 lose a quoted literal and only 4 literals
  are affected. Three of the four are 1.5.5 smali dumps disappearing: e.g.
  `"scene_estimate"` becomes `CashierExceptionSceneKt.E_SCENE_ESTIMATE`, the real
  source-level constant reference. The fourth is inside `ConfirmFragmentEx.g0`,
  the regressed method. Kotlin enums also restore properly now
  (`public enum DialogType { TAKE_PHOTO_PAGE; }` instead of a desugared class
  calling `new DialogType("TAKE_PHOTO_PAGE", 0)`), so an enum constant reads as
  an identifier rather than a quoted string — it survives quoted in the
  `@Metadata` blob either way.
- *Branch conditions.* 49 hunks in the rendering-only group touch an `if`. Every
  one is a semantics-preserving rewrite: nested ternaries expanded into `if/else`
  chains, De Morgan inversion with the branches swapped, `try`/`catch` re-nested
  to match the original shape. All are easier to read, none changes meaning.

The one drift worth knowing about: **jadx-invented local variable names move**
(83 of 224 rendering hunks are pure identifier renames — `strEyo` → `strAu`,
`o_mr12` → `o_mr2`). Class, method and field aliases do not (§2b). A finding that
quotes a local variable name will drift; one that quotes a class or method name
will not.

## 2b. Alias-name stability — the gate this upgrade was held behind

Deobfuscated names are what the caller records findings against, and
`get_class_source` rejects a name it does not recognise. Measured on a large production APK
by dumping raw-dex-identity → alias for every class, method and field, then
diffing key by key:

| | classes | methods | fields |
|---|---|---|---|
| Names | 141,461 | 872,119 | 860,163 |
| 1.5.5 load 1 vs load 2, same JVM | \| | identical | \| |
| 1.5.5 vs 1.5.5, separate JVMs | \| | identical | \| |
| **1.5.5 vs 1.5.6** | \| | **identical** | \| |
| added / removed / changed | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |

All four dumps are byte-identical; DIVA likewise. 47,996 of the 141,461 classes
carry a generated alias, including the 12,568 `C####X` names that are the fragile
kind — `com.usdk.android.C29382G` lands on the same line of both dumps.

Both loads ran with `GeneratedRenamesMappingFileMode.READ` and
`generatedRenamesMappingFile == null`, with no `.jobf` beside either APK, so each
recomputed its names rather than replaying a cache. Pinning via
`setGeneratedRenamesMappingFile` is therefore not needed today — but it is the
fix if a future version ever moves a name.

`AliasStabilityTest` keeps the load-to-load half of this honest in CI.

## 3. `getUsed()` — the direction the xref tools do not have

Task 2 shipped "who calls X" (`getUseIn()`). 1.5.6 adds the inverse.

```java
Set<MethodNode>   MethodNode.getUsed();            // callees inside the APK
List<MethodInfo>  MethodNode.getUnresolvedUsed();  // callees OUTSIDE the APK
boolean           MethodNode.callsSelf();          // direct recursion
```

Same story as `getUseIn()`: populated during `load()`, not on demand.

| | DIVA | a large production APK |
|---|---|---|
| Per-call `getUsed()` (2000 calls) | **0.0006 ms** | — |
| Resolved call edges, whole APK | 14,387 | 1,383,182 |
| **Unresolved (leaving the APK)** | 14,073 | **721,397** |
| Methods with callees | 7,288 | 502,174 |
| Directly recursive methods | 31 | 1,619 |
| Walking *every* method's callees | 5 ms | 6,584 ms |

Note the asymmetry in the last row: a single lookup is free, a whole-APK sweep of
`getUsed()` is seconds. That is fine — a `get_callees` tool only ever asks about
one method.

### 3a. `getUsed()` is not safe to read from a shared daemon

The section above is right about the numbers and wrong about the data. Measured
later, after `get_callees` had shipped on top of it:

**`getUsed()` is order-dependent. Decompiling a class deletes call edges from it.**

jadx's usage graph describes the Java it intends to *print*, not the dex.
Decompilation rewrites it in place:

- `InlineMethods.updateUsageInfo` folds a synthetic accessor into its callers and
  re-points the accessor's own edges to them
- `ClassModifier.modifySyntheticMethod` → `UsageInfoVisitor.replaceMethodUsage`
  does the same for synthetic constructors
- `MethodNode.getUsed()` then drops, **on read**, every callee whose `getUseIn()`
  no longer names this method — `removeInvalidMethodsUsed()` mutates the set

| after decompiling | DIVA (all 651 top-level) | a large production APK (3,000 of 141,461) |
|---|---|---|
| methods reporting **fewer** callees | 699 | 2,723 |
| resolved edges lost | 963 | 3,194 |
| edges gained | 0 | 0 |
| methods left reporting *no* in-APK callee | 374 | — |
| `getUnresolvedUsed()` edges changed | **0** | **0** |
| `getUseIn()` edges lost / gained | 1,047 / 137 | 3,593 / 834 |
| method aliases changed | — | 514 of 872,113 |

The dex is the truthful graph, and the dropped hop is real. In the smali,
`FloatingActionButtonEclairMr1$ElevateToTranslationZAnimation.getTargetShadowSize`
is two `invoke-static` instructions to `access$400` and `access$500`; the warm
graph reports zero. An agent has to follow those accessors to reach what the
method reads.

Three consequences, in descending size:

1. **`get_callees` now reads the dex, not the graph** —
   `JadxAnalyzerCore.scanCallees` walks `MethodNode.getCodeReader()`, which is a
   `final` private copy of the dex bytes that no pass can rewrite. It is
   `UsageInfoVisitor.processInsn`'s own `METHOD_REF` / `CALL_SITE` handling, so
   cold answers are unchanged: compared per method against the pristine graph,
   **0 mismatches over 14,809 (DIVA) and 872,119 (a large production APK) methods**. Cost:
   0.0008 ms/method, 710 ms to scan the whole a large production APK APK — cheaper than the
   6,584 ms `getUsed()` sweep in the table above, with no load-time or memory
   cost at all. End to end `get_callees` went 1.0698 → 1.0816 ms/call on
   a large production APK (+1.1%, inside noise); that millisecond is `findClassNode`'s linear
   scan over 141,461 classes and predates this.
2. **`find_sink_call_sites` is unaffected**, as claimed —
   `getUnresolvedUsed()` never moved, and a full sweep before and after returns
   the same 4,125 call sites.
3. **`get_xrefs_to_method` *is* affected** — `getUseIn()` is the list
   `InlineMethods` edits, and it both loses and gains entries. Not fixed at the
   time: unlike callees, "who calls X" cannot be read out of X's own dex. Closed
   in [§3b](#3b-the-reverse-direction-closed).

Probes: `CalleeStabilityProbe` (which edges move), `CalleeEdgeDiffProbe` (which
names), `CalleeDexEquivalenceProbe` (dex vs pristine graph, plus cost),
`ToolStabilityProbe` and `SinkSweepStabilityProbe` (the three tools end to end).
`CalleeStabilityTest` keeps it from coming back.

### 3b. The reverse direction, closed

"Who calls X" cannot be read out of X's own dex, but it can be read out of
*everyone else's*: the forward scan already existed, and inverting it over every
method gives caller edges no pass can rewrite. That is
`core/DexReverseIndex.java`, and all three `get_xrefs_to_*` tools plus
`findSinkCallSites`' in-APK override resolution now read it instead of
`getUseIn()`.

### The damage it replaces

Four passes rewrite the reverse edges, not the two that broke `getUsed()`:
`UsageInfoVisitor.replaceMethodUsage` (which *empties* the replaced method's
caller list), `InlineMethods.updateUsageInfo`, `InlineMethods.replaceClsUsage`
and `ProcessAnonymous`.

| after decompiling | DIVA (all 1,791) | a large production APK (3,000 of 141,461) |
|---|---|---|
| `MethodNode.getUseIn` keys moved | 988 | 1,536 |
| — edges lost / gained | 1,343 / 380 | 1,800 / 722 |
| — methods left with **no** caller at all | 692 | 883 |
| `FieldNode.getUseIn` keys moved | 983 | 1,458 |
| — edges lost / gained | 389 / **2,175** | 76 / **4,754** |
| `ClassNode.getUseInMth` keys moved | 2 | 46 |
| `ClassNode.getUseIn` keys moved | 59 | 165 |

Fields are the surprise: they mostly *gain*. `InlineMethods` re-points a folded
accessor's field accesses at whoever it was folded into, so a field ends up
naming a method whose own bytecode never touches it.

### Why it can be lazy

The index's inputs had to be shown immutable, not assumed so. `DexTreeStabilityProbe`
decompiles the APK and re-derives them: on DIVA (all 1,791 classes) and on
a large production APK (6,000 classes) the class, method and field enumerations and **every
resolved caller→callee edge the dex names** — 14,418 and 1,384,801 — come back
identical, 0 lost, 0 gained. So the build answers the same thing whenever it
runs, and the only question left is who waits for it.

### Correctness: three of four maps are byte-identical to jadx's cold graph

`XrefDexEquivalenceProbe`, against the *pristine* graph, nothing decompiled:

| | DIVA | a large production APK |
|---|---|---|
| `MethodNode.getUseIn` | 0 mismatches / 14,809 | 0 / 872,119 |
| `FieldNode.getUseIn` | 0 / 9,643 | 0 / 861,374 |
| `ClassNode.getUseInMth` | 0 / 1,791 | 0 / 141,461 |
| `ClassNode.getUseIn` | +251 edges, −0 | +34,037, −0 |

The one divergence is deliberate and fully classified: **every** extra is an
anonymous class. `ProcessAnonymous.markAnonymousClass` runs during `load()` and
`safeRemove()`s an anonymous class from its outer class's `useIn`, because it
will be printed inline — so jadx's *cold* answer is already a codegen view, not
the dex. The dex says `NavigationMenuPresenter$1` really does reference
`NavigationMenuPresenter` (its `this$0` field, its constructor argument), and for
a caller that is a real, separately-addressable code location. jadx's version
also flips back when `undoAnonymousMark` runs later, which is where DIVA's 134
"gained" class edges came from.

Two parity details cost real edges and are worth naming, because both were found
by measurement rather than by reading:

- `UseSet.add` opens with `if (key == value) return`, so jadx records **no
  self-edges**. Without that, 31 recursive methods on DIVA gained themselves as
  a caller and 1,015 classes gained themselves as a user.
- `UsageInfo.processType` recurses into `getWildcardType()`. Dropping it lost
  exactly one edge on DIVA and it was a real one: `CoordinatorLayout`'s
  `@DefaultBehavior` declares `Class<? extends Behavior> value()`, so the only
  thing naming `Behavior` there is the bound inside the wildcard.

### Ground truth, not self-consistency

A stable wrong answer is worse than an unstable one, so `XrefSmaliGroundTruthProbe`
rebuilds the caller set from the `invoke-*` lines of the smali itself and
compares: **200 sampled target methods, 200 agree, 0 invented callers, 0 dropped
callers.** `XrefStabilityTest` also pins one answer by hand —
`TabLayout;->access$100` is the target of exactly four `invoke-static`
instructions in the APK, all four inside `TabLayout$Tab`.

### Cost

| | a large production APK (141,461 classes, 872,119 methods) |
|---|---|
| load | 13.6 s |
| index build (scan + compaction) | **3.1 s**, 819,305 methods scanned, 0 errors |
| edges kept | 1,383,182 caller + 1,205,592 field + 1,776,493 class-in-method + 935,369 class |
| retained heap | **88 MB** |
| sink sweep, first call (builds the index) | 3,336 ms |
| sink sweep, every call after | 144–155 ms — unchanged |

**Lazy, not eager**, because the build costs the same whenever it runs: eagerly
it lands on every `load()`, including the loads whose caller never asks for an
xref; lazily one request pays it once and it is kept for the life of the APK.
`/health` reports `reverseIndex` so that request is identifiable.

**`AnalyzerRegistry`'s constants are left alone**, and that is a measurement, not
an oversight: 88 MB is 3% of a warm APK's 2,943 MB and 1.4% of the 6,144 MB
`PER_APK_BUDGET_MB` slot, so `defaultCapacity()`'s arithmetic does not move.

Compaction was worth measuring separately — a first version that reused one
`LinkedHashSet` across all keys spent **9.0 s** there against 2.2 s for the whole
dex scan, because `clear()` walks a table that had already grown to fit the
widest key in the APK (61,910 users), and all 1,141,709 keys paid for it. 542,783
of those keys (48%) have exactly one user and now allocate no Set at all.

### What is still order-dependent

Only the **method alias**, which this does not touch and which was already
written up above (514 of a large production APK's 872,113 aliases move). Decompiling removes a
synthetic bridge and re-aliases the method left behind, so the same call site is
reported as `invoke2` before and `invoke` after. Verified on a live daemon on
a large production APK after 6,000 classes were decompiled through 16 concurrent clients:
the widest field xref (`kotlin.Unit.INSTANCE`, 6,510 entries) and the full sink
sweep (1,214 call sites) are **identical once the alias is projected out — 0
lost, 0 gained** — with 12 and 2 entries respectively reported under a renamed
alias. `the analysis client`'s `the client's tool reference` says exactly this, and its
old "an empty caller list is not proof" warning is gone.

### Concurrency

Same shape as `AnalyzerRegistry`: volatile read on a hit, double-checked build
inside the monitor. 24 clients issuing their first xref request simultaneously
against a freshly loaded a large production APK produced **one** build in the daemon log and
24 identical answers in 3.19 s total.

Probes: `XrefStabilityProbe` (which edges move), `DexTreeStabilityProbe` (are the
index's inputs immutable), `XrefDexEquivalenceProbe` (index vs pristine graph),
`XrefSmaliGroundTruthProbe` (index vs smali), `ReverseIndexCostProbe` (time and
heap). `XrefStabilityTest` keeps it from coming back.

## 4. `getUnresolvedUsed()` — sinks, for free

The unexpected one. A call that leaves the APK is a call into the framework, and
a call into the framework is what a sink *is*. That makes sink discovery a
metadata lookup instead of a decompilation problem.

Sweeping the entire 141,461-class APK for eight sink types, **no decompilation**:

```
whole-APK sink sweep via getUnresolvedUsed(): 104 ms

android.content.Context.startActivity          553 call sites
java.io.FileOutputStream.write                 149 call sites
android.webkit.WebView.loadUrl                  85 call sites
java.lang.Runtime.exec                          53 call sites
android.webkit.WebSettings.setJavaScriptEnabled 47 call sites
android.content.Context.sendBroadcast            39 call sites
android.webkit.WebView.addJavascriptInterface    30 call sites
android.content.Intent.parseUri                   7 call sites
      com.example.webview.AppWebViewClient.openThirdPartyAppWithIntentScheme
      com.example.soda.web.overriders.CommonUrlOverrider.shouldOverrideUrlLoading
      com.bytedance.sdk.openadsdk.core.widget.uc.rw.shouldOverrideUrlLoading
```

Those `Intent.parseUri` sites are the intent-redirection pattern the caller
exists to find, surfaced in a tenth of a second from an APK nobody had triaged.
a survey worker currently imports facts of exactly this shape from a separate
apk-analyzer run; this would produce them natively.

## 5. `jadx-analysis` — a real call graph

New module at 1.5.6 only (`io.github.skylot:jadx-analysis:1.5.6`, 22 classes).
Concrete classes are package-private; the public surface is small and clean:

```java
ICallGraph g = JadxCallGraph.builder(jadx)
        .includePackages("com.example.app")   // optional scope
        .resolvedOnly(false)               // keep framework edges
        .build();
List<ICallGraphEdge> edges = g.edges();    // each edge: from() / to() / isResolved()
g.writeDot(path);  g.writeJson(path);
```

| Build | DIVA | a large production APK (141k classes) |
|---|---|---|
| Full graph | 19 ms (28,460 edges) | **413 ms (2,104,579 edges)** |
| `resolvedOnly(true)` | 5 ms (14,387) | 302 ms (1,383,182) |
| `includePackages(one package)` | 0 ms (48) | **22 ms (2,758)** |
| Indexing both directions in a map | 13 ms | 942 ms |

A forward walk from a real entry point, which is the shape a sink tracer needs:

```
forward walk from com.example.trackupload.sdk.storage.DaoMaster.OpenHelper.onCreate:
  -> com.example.sdk.apm.SystemUtils.log
    -> com.example.sdk.logging.Logger.log
    -> com.example.sdk.logging.LoggerFactory.getLogger
  -> com.example.trackupload.sdk.storage.DaoMaster.createAllTables
    -> com.example.trackupload.sdk.storage.BizNodeEntityDao.createTable
```

**This should delete code, not add it.** `JadxAnalyzerCore.generateCallGraphForMethod`
currently finds callers by regex-matching decompiled text — `methodCallsTarget()`
searches for `methodName(` in class source and `findCallersRecursively()` calls
`getCode()` on every class in the APK. That is the same decompile-the-world
pattern that cost 71.6 s in the old `searchMethodByName`, and it is still in the
tree. 413 ms of maintained, dex-level graph replaces it outright.

> **Outcome: the first half was right and the second half was not.** The regex
> implementation is deleted. Nothing replaced it, and `jadx-analysis` was
> dropped from `pom.xml` with it — see [§C](#c-replace-generatecallgraphformethod-with-jadx-analysis)
> for why a graph that costs 413 ms to build has no caller to serve.

## 6. Smaller additions

- **`JavaClass.loadingWouldRequireDecompilation()`** — 0 ms, and it answers "is
  this call about to be expensive?" before making it. Directly useful given this
  codebase's standing rule against whole-APK decompilation; a bulk operation
  could skip or defer classes that are not warm yet.
- **`ClassNode.getInnerClassesRecursive(Set)`** — relevant to the inner-class
  work, which currently walks `getInnerClasses()` one level.
- **`callsSelf()`** — cheap recursion guard for any future graph walk (1,619
  directly recursive methods on a large production APK, each a potential non-terminating walk).

## Recommended features

Ordered by value per unit of work. All three depend on the 1.5.6 upgrade landing
first; none requires the others.

### A. `get_callees(className, methodName)` — highest value, smallest change

Completes the pair the xref work started. Today an agent can ask who calls a
method but not what it calls, so walking *forward* — which is what sink tracing
is — means decompiling and reading source.

```
get_callees(className, methodName) -> {
    "callees":    [{className, methodName, signature}],   // resolved in this dex
    "external":   [{className, methodName, signature}],   // not resolved -> sinks
    "callsSelf":  bool
}
GET /api/jadx/callees?className=…&methodName=…  ->  {"callees": {...}}
```

Splitting internal from external is the point: `external` is the sink list for
that method, already filtered.

Cost ~0 ms. The implementation is a near-copy of `getXrefsToMethod` — same
target-resolution, same `refEntry` shape, opposite edge direction. Roughly a
day's work including tests across all four layers.

#### Shipped — and "~0 ms" was wrong

Built as specified. Two things the estimate above got wrong, both measured on
a large production APK with `AppWebViewClient.shouldOverrideUrlLoading` (13 internal +
14 external edges), 2000 calls each after warm-up:

| | per call |
|---|---|
| `getCallees` (the whole tool, in-JVM) | **1.51 ms** |
| `getXrefsToMethod`, same target | 1.05 ms |
| `searchJavaClassByAliasFullName` alone | **1.31 ms** |
| `getUsed()` + `getUnresolvedUsed()` alone | 0.069 ms |
| REST round trip through the daemon | 3.1 ms median (n=50) |

The forward-edge metadata really is nearly free, as §3 said. What is not free is
**resolving the class name**, which is a linear scan of 141,461 classes and is
87 % of the call. That cost is not new and not this tool's: `getXrefsToMethod`
pays exactly the same 1.31 ms and always has. So "~0 ms" is right about the
feature and wrong about the call — anything built on top should hold a resolved
target rather than re-resolving per query, and a per-class index is the obvious
win for *all* the name-addressed tools, not just this one.

Second correction, to the contract rather than the cost: **`external` is defined
by resolution, not by package.** `getUnresolvedUsed()` returns the invoke's
declared receiver, so an inherited framework method arrives named after the
in-APK subclass — `jakhar.aseem.diva.LogActivity.findViewById`, not
`android.app.Activity.findViewById`. Still correct as a sink list (it is a call
this dex cannot follow), but a consumer that filters `external` by "is the
package android.*" will drop real entries.

Verified end to end on the real APK. `openThirdPartyAppWithIntentScheme` returns
0 internal and 9 external, including `android.content.Intent.parseUri` and
`android.content.Context.startActivity` — §4's intent-redirection finding,
reproduced through the shipped tool with no decompilation.

### B. `find_sink_call_sites(sinks[])` — the most interesting

A whole-APK sweep that answers "where does this app touch any of these
framework methods", in ~100 ms, with no decompilation.

```
find_sink_call_sites(sinks: list[str]) -> {sink: [{className, methodName}]}
GET /api/jadx/sink-call-sites?sinks=android.webkit.WebView.loadUrl,…
```

This changes what phase 0.5 of an analysis can do. a survey worker presently imports
JS bridges, WebViewClients and `Intent.parseUri` call sites from a separate
apk-analyzer run, and an analysis without that run proceeds blind. Native support
removes the dependency and makes the survey a default rather than an optional
import.

Worth pairing with `references/sink-catalog.md` so the default sink list is the
one the caller already reasons about.

#### Shipped — and exact name matching was not enough

Built as specified, plus a default sink list and a cap. Cost held: the full
default catalogue over all 141,461 classes and 721,397 unresolved edges is
**65–135 ms in-JVM** and **70–140 ms through the daemon**, JSON encoding and the
loopback hop included. `SinkCallSitesTest` asserts under a second, and asserts
separately — via `loadingWouldRequireDecompilation()` — that the sweep leaves
every class cold, so the claim cannot pass by being on a fast machine.

**The correction is to §4's matching, not its timing.** §4 counted a call site
when `declClass.getFullName() + "." + getName()` equalled the sink. But
`getUnresolvedUsed()` reports the receiver's *static type at the call*, not the
class that declares the method, so a subclass that inherits a sink arrives under
its own name. Three rules, measured side by side on a large production APK
(`SinkSweepProbe`):

| sink | exact | subtype | name-only |
|---|---|---|---|
| `WebView.loadUrl` | 85 | **91** | 91 |
| `WebView.addJavascriptInterface` | 30 | **33** | 33 |
| `Context.startActivity` | 553 | **696** | 701 |
| `FileOutputStream.write` | 149 | **149** | 1,428 |
| `Runtime.exec` | 53 | 53 | 53 |
| `Intent.parseUri` | 7 | 7 | 7 |

The six `loadUrl` call sites exact matching drops are
`com.facebook.ads.redexgen.X.{O6,SX,T5,TE}` — obfuscated in-APK **WebView
subclasses**, which is the single surface a WebView analysis most wants. Name-only
recovers them and then adds 1,279 `write` calls to things that are not files.
So the shipped rule is *receiver is the named class or a subtype of it*, via
`ClspGraph.isImplements` — which is a lookup in a map `load()` already built, is
documented by its bytecode to return `false` rather than throw for a class it
has never heard of, and cost nothing measurable across 6,417 distinct receiver
pairs. §4's 7 `Intent.parseUri` sites reproduce exactly, `AppWebViewClient`
included.

Two further things §4 could not have known:

- **A bundled SDK is invisible to this tool.** It sees calls that *leave* the
  dex. `CustomTabsIntent.launchUrl` measured 0 hits on a large production APK not because the
  app avoids custom tabs but because androidx ships inside the APK, so the call
  resolves. That is why `external_browser_load` is not in the default list: a
  key that structurally cannot fire reads as "none here", which is a lie. Same
  reason `data_exfil` is out — `android.util.Log.*` is 1,473 call sites, 27 % of
  everything the catalogue matches, and would spend the whole cap on noise.
- **The payload needs a cap, and the cap needs to be visible.** Uncapped, the
  default sweep of a large production APK is 5,491 call sites and 662 KB of JSON. Capped at
  100 per sink it is 208 KB, and the seven sinks that hit the cap are named with
  their true totals under `@truncated` (`intent_launch` 954, `class_load` 752,
  `parcelable_extra_injection` 630 …). A list silently cut to its first N reads
  as the whole truth, which is worse than a big response.

### C. Replace `generateCallGraphForMethod` with `jadx-analysis`

Not a new capability — a deletion. The existing implementation is the last
decompile-the-world path in the codebase, and it is reachable from the CLI.

Suggested shape: build the graph once per APK in `AnalyzerRegistry` beside the
existing warm-load (413 ms on the worst APK measured, against an 11 s load), then
serve caller/callee/path queries from an index. Or build scoped per query at
22 ms if the memory of a 2.1 M-edge graph is not wanted.

This is the largest of the three and the least urgent, because nothing in the
caller calls the CLI call-graph path today — but it removes a real performance
trap from the tree.

#### Outcome: deleted, and not replaced

The "delete" half shipped. The "replace" half did not, and `jadx-analysis` came
back out of `pom.xml`. Three measurements decided it.

**1. The old implementation could not answer the question it advertised.** The
CLI prompt read `Enter method name to trace (e.g., loadUrl, WebView.loadUrl)`.
Run on DIVA, that exact example returned **`Method not found: loadUrl` after
1,541 ms**. `findTargetMethods` walks `jadx.getClasses()`, so it can only find
methods *declared inside the APK* — every framework sink, which is the entire
category a deeplink analysis cares about, is invisible to it. DIVA does call
`WebView.loadUrl`, from `InputValidation2URISchemeActivity.get`;
`find_sink_call_sites(["loadUrl"])` returns that one call site in **5 ms**.
Same question, right answer, 300× faster.

It had a second blind spot of the same kind: `jadx.getClasses()` is the
**top-level** class view. On a large production APK it yields **72,345** classes where jadx's
own load log reports **141,461** — so 69,116 inner and anonymous classes, which
is exactly where listeners and callbacks live, were invisible to
`findTargetMethods`, `findCallersRecursively` and `getSimilarMethods` alike.
`get_class_source` was fixed for this; the call graph never was. The tool being
removed was not a slower version of something useful — it was wrong twice over.

And on a real APK it did not return at all. A **single-target** trace —
`com.example.webview.AppWebViewClient.openThirdPartyAppWithIntentScheme`,
one node, so exactly one whole-APK `getCode()` pass before any recursion — was
**killed at 25 minutes** on a large production APK with no result, no `OutOfMemoryError` and
no exception, holding **13.4 GB RSS** under `-Xmx12g`. Its last log line was at
2.7 minutes; the remaining 22 were spent silently decompiling. The 71.6 s
`searchMethodByName` figure that made this pattern notorious was the *cheap*
example of it.

**2. Nothing could reach it.** No REST endpoint, no MCP tool, no test. The only
caller was menu entry 4 of the interactive CLI, which the caller never runs. The
`getUsed()`-based pair that *is* exposed — `get_callees` forward,
`get_xrefs_to_method` backward, `find_sink_call_sites` for the whole-APK inverse
— covers every call-graph question the caller's workers actually ask. Every
`agents/*.md` tool list names those three and nothing graph-shaped; the tracers
walk **one hop at a time and read source at each hop**, because what they need
from a hop is the *guard*, not the edge. `the client's tool reference` states
that limit for `get_callees` in as many words: "it reports that a call exists,
not the condition under which it is reached."

**3. A transitive graph would not have earned its memory.** Re-measured on the
large APK, with retained heap taken after a forced GC:

| | a large production APK |
|---|---|
| `jadx.load()` | 13.8 s, 72,345 top-level classes, **2,957 MB** warm |
| `JadxCallGraph.builder(jadx).build()` | **336 ms**, 2,104,579 edges, **+133 MB** |
| indexing both directions, which a caller/callee query server needs | **+666 ms**, 499 k / 508 k keys, **+752 MB** |
| total for the suggested shape | **+885 MB per warm APK, +30 %** |

The 413 ms build and the 2,104,579 edge count above both hold up (336 ms here,
same edge count). What §5 did not price is the index: holding a queryable graph
costs 885 MB *per APK*, in a daemon whose entire design is an LRU of warm APKs.
That is a 30 % memory tax for a capability with no caller and a known blind spot
— and the 22 ms scoped build, the cheaper alternative, only ever answers within
one package, which a taint trace crossing SDK boundaries cannot use.

**What is gone:** `generateCallGraphForMethod`, `CallGraphResult`,
`findTargetMethods`, `findCallersRecursively`, `methodCallsTarget`,
`findEntryPoints`, `getSimilarMethods`, `model/CallGraphNode.java`, the CLI's
`generateCallGraphForMethod` / `printCallTree` / `printIndented` and menu entry 4
(entries renumbered 4–13), and the `jadx-analysis` dependency. `extractMethodCode`
stays — `getMethodSource` uses it too. **No decompile-the-world loop remains in
the tree.**

If a call graph is ever genuinely wanted, this section is the spec and the
numbers above are the budget. The trigger to revisit is a *named consumer* — a
worker that asks "does anything reach X" and cannot get there one hop at a time.

### Not recommended

- **Whole-APK `getUsed()` sweeps.** 6.5 s on a large production APK — and the answer is only
  right if nothing has been decompiled yet ([§3a](#3a-getused-is-not-safe-to-read-from-a-shared-daemon)).
  Walking the dex instructions instead is both truthful and faster: 710 ms.
  Per-method lookups only;
  if a bulk view is wanted, build the `jadx-analysis` graph instead — it produces
  more, faster. *(Superseded by feature B: `find_sink_call_sites` sweeps
  `getUnresolvedUsed()` in ~104 ms, and is what shipped.)*
- **Adopting `jadx-analysis` without the 1.5.6 upgrade.** It has no 1.5.5 release.
  *(Moot — `jadx-analysis` was not adopted at all; see §C's outcome.)*

## Suggested order

1. **Upgrade to 1.5.6 alone**, own commit, full suite plus a spot-check that
   decompiled output still reads the way the agent prompts expect. Cheap to
   revert if anything surprises.
2. **A**, because it is small and completes an existing pair.
3. **B**, which is where the analysis leverage actually is.
4. **C**, when the regex call graph next causes trouble. *(Done, as a straight
   deletion — see §C's outcome. All four are now closed.)*

## Appendix: reproducing the measurements

These probes were written against 1.5.6 and are not in the build, because they
do not compile against 1.5.5. Drop into
`src/test/java/com/example/jadxmcpserver/core/` after upgrading and run with
`mvn exec:java -Dexec.classpathScope=test -Dexec.mainClass=…`.

### Forward edges, recursion, decompilation guard

```java
// Per-call cost of getUsed(), and the whole-APK totals in section 3.
for (ClassNode c : jadx.getRoot().getClasses()) {
    for (MethodNode m : c.getMethods()) {
        edges      += m.getUsed().size();
        unresolved += m.getUnresolvedUsed().size();
        if (m.callsSelf()) { recursive++; }
    }
}
// JavaClass.loadingWouldRequireDecompilation() measured 0 ms over 200 classes.
```

### Sink sweep (section 4)

```java
Map<String, List<String>> callers = new LinkedHashMap<>();
for (String s : SINKS) { callers.put(s, new ArrayList<>()); }

for (ClassNode cls : jadx.getRoot().getClasses()) {
    for (MethodNode mth : cls.getMethods()) {
        for (MethodInfo callee : mth.getUnresolvedUsed()) {
            String full = callee.getDeclClass().getFullName() + "." + callee.getName();
            List<String> hits = callers.get(full);
            if (hits != null) {
                hits.add(mth.getMethodInfo().getAliasFullName());
            }
        }
    }
}
```

### Call graph (section 5)

```java
ICallGraph graph = JadxCallGraph.builder(jadx).build();
Map<String, Set<String>> callers = new HashMap<>(), callees = new HashMap<>();
for (ICallGraphEdge e : graph.edges()) {
    String from = e.from().getMethodInfo().getAliasFullName();
    String to   = e.to().getMethodInfo().getAliasFullName();
    callers.computeIfAbsent(to,   k -> new LinkedHashSet<>()).add(from);
    callees.computeIfAbsent(from, k -> new LinkedHashSet<>()).add(to);
}
```

Requires `io.github.skylot:jadx-analysis:${jadx.version}` in `pom.xml` — which is
**no longer there** (§C's outcome removed it), so re-add it before rerunning this
probe. The `heapBaseline` / `retained` numbers in §C's outcome table come from
this probe with a `System.gc()` + `totalMemory() - freeMemory()` reading taken
before the build, after the build, and after indexing.

### Output-stability diff (section 2)

Decompile the first 60 classes under each version into a file and `diff` them;
run each version by putting the matching `jadx-core` / `jadx-dex-input` /
`jadx-input-api` / `jadx-zip` jars first on the classpath rather than by changing
`pom.xml`, so both can run without a rebuild.
